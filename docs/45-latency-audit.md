# 45. 대기 시간 · 런타임 점검 (2026-09-24)

> 창업자: "들어가는 대기 시간과 런타임이 느려지는 경우가 계속 있다 — 지금의 체계는 잃지 말고, 호출 · 런타임 · 화면 전환의 지연을 전부 검증하고 보완."
> 원칙: 결과(코스 · 화면 · 문구)는 그대로, 같은 계산을 **다시 하지 않게** 하거나 **기다리지 않게**만 바꾼다.

## 1. 무엇이 느렸나 — 잰 값

### 웹: 대부분은 `next dev` 자체
같은 화면을 개발 모드(3000)와 운영 빌드(3100)로 쟀다(Playwright + 시스템 Chrome, 430px, 다시 열기 3회 중앙값).

| 화면 | dev 첫 방문 | dev 다시 열기(load / 다 뜰 때까지) | 운영 첫 방문 | 운영 다시 열기(load / 다 뜰 때까지) |
|---|---|---|---|---|
| `/` | 3.0 s | 2.5 / 3.4 s | 3.2 s | 0.12 / 0.8 s |
| `/explore` | 4.3 s | 2.9 / 3.0 s | 1.6 s | 0.18 / 1.3 s |
| `/plan` | 3.1 s | 1.9 / 2.6 s | 0.9 s | 0.12 / 0.8 s |
| `/course/[id]` | **73 s** | 2.8 / 5.0 s | 2.1 s | 0.15 / 1.4 s |
| `/my` | **40 s** | 2.4 / 3.9 s | 1.0 s | 0.10 / 0.9 s |

- dev 는 화면을 **처음 열 때 그 자리에서 컴파일**한다(OneDrive 안이라 더 느리다) — 수십 초 대기의 정체. JS 도 압축 전 6.4MB(운영 120~280KB).
- 그래서 "사용자가 받는 속도"는 운영 빌드로 봐야 한다 → `npm run preview:prod` (아래).

### API
| 호출 | 전 (warm) | 후 (warm) | 한 일 |
|---|---|---|---|
| `GET /attractions?limit=24` (둘러보기 · 더 보기마다) | 553 ms | **15 ms** | 질문(지역 · 유형 · 날짜 · 검색어)별 5분 캐시. 더 보기가 전체 목록을 다시 계산하던 것 |
| `GET /courses/{id}/stops/{n}/candidates` (바꾸기 시트) | 1,558 ms | **29 ms** (첫 열기 1.2 s) | 코스 상태(장소 순서) + 보는 사람별 10분 캐시. 바꾸기 · 순서 변경이 키를 바꾼다 |
| `GET /meta/regions/{slug}` (위저드) | 429 ms | < 30 ms | 목록과 같은 1시간 캐시 |
| `localhost` 새 연결 하나 | +200 ms | **+2 ms** | 아래 §2 |
| `POST /courses/generate` | 3.3~4.1 s | 그대로 | 엔진 본체 — 결과가 바뀔 수 있어 이번에 손대지 않았다 |

- 코스 생성이 다른 요청을 막는지 확인: 생성 중에도 다른 요청은 10~60 ms — 막지 않는다(수정 불필요).
- 캐시는 관리자 "캐시 비우기" 기본 목록에 `region:one` · `cand:` · `attractions:` 를 넣었다. 관리자가 장소를 승인해도 둘러보기에는 최대 5분 뒤 보인다.

## 2. `localhost` 한 번에 0.2초
Windows 는 `localhost` 를 IPv6(::1)로 먼저 찾는데 API 가 127.0.0.1 만 듣고 있었다 → 새 연결마다 ::1 이 거절되고 IPv4 로 다시(브라우저 · Node 0.17~0.2 s, 파이썬 2 s).
웹 주소를 127.0.0.1 로 바꾸면 로그인 쿠키가 다른 사이트로 취급될 수 있어 **API 가 둘 다 듣게** 했다:

```
cd apps/api && uv run python -m app.devserver      # 127.0.0.1 + ::1, 로컬에서만
```
운영(Docker · Render)의 실행 명령은 그대로다. 코드 자동 반영이 필요하면 예전처럼 `uvicorn --reload`(이 지연은 남는다).

## 3. 운영 빌드로 로컬에서 보기
```
cd apps/web && npm run preview:prod      # → http://localhost:3100
```
소스를 OneDrive 밖(`%LOCALAPPDATA%\naegajjanday\webprod`)에 복사해 거기서 빌드한다 — 이 폴더에서 `next build` 를 돌리면 돌고 있는 dev 의 `.next` 가 깨진다(docs/40). API 의 CORS 기본값에 `http://localhost:3100` 을 넣었다.
- Windows 에서 `fs.cpSync` 가 이 경로(한글 + OneDrive)에서 node 를 0xC0000005 로 죽인다 → robocopy 를 쓴다.
- 빌드 끝의 `EPERM symlink … standalone` 과 "next start does not work with output: standalone" 경고는 Docker 용 설정 때문이고 로컬 미리보기는 정상 동작한다.

## 4. 남은 것
- 코스 생성 3~4 s: 엔진 단계별 시간(후보 조회 · 조합 · v2 구조 대안 · 이동 시간)을 재서 결과가 같은 범위 안에서 줄일 곳 찾기 — `eval-courses --compare` 로 결과 동일성을 확인하며.
- 바꾸기 시트 첫 열기 1.2 s: 결과 화면이 뜬 뒤 한가할 때 첫 장소만 미리 받아 두는 방법(서버 부하와 저울질).
- 운영 캐시는 Redis(`REDIS_URL`) — 지금은 프로세스 메모리라 재시작하면 비워진다.
