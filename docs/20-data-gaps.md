## 공식 데이터로는 안 되는 것 (분명히 해 둔다)

| 하고 싶은 것 | 결론 | 대안 |
|---|---|---|
| 가게별 리뷰 · 별점 | 공개 데이터 없음 | 위 1 · 2 · 5번의 묶음(인증 + 업력 + 실제 이동 행동)으로 대신한다. 우리 서비스 안에서 쌓이는 피드백(코스 저장 · 바꾸기 · 평가)도 시간이 지나면 신호가 된다 |
| 가게별 메뉴 가격 | 착한가격업소가 사실상 유일 | 실측가 → 시도 × 업종 추정가 2단 구조, 추정임을 화면에 밝힌다 |
| 일반 식당의 영업시간(전국) | 공식 소스 없음. OSM `opening_hours` 는 한국 전체 1만여 건뿐 | 업종 기본 영업시간 + "방문 전 확인" 안내 + 지도 앱 링크(저장 없이) |
| **KBO 경기 일정** | **공식 오픈 API 없음.** 공개된 "KBO API"는 모두 홈페이지 크롤러라 우리 원칙상 쓸 수 없다 | ① 1군 9개 구장을 놀거리로 등록(좌표는 체육시설 데이터) + "오늘 경기 확인"은 KBO 공식 일정 페이지로 링크 ② 시즌 일정표를 운영자가 직접 입력(우천 취소는 반영 못 하므로 "일정은 바뀔 수 있어요" 고지) ③ 공식 기록 위탁사(스포츠투아이)와 계약 |
| 숙박 실시간 요금 | 공식 데이터 없음 | TourAPI "참고 요금" 라벨. 실요금은 OTA 제휴(어필리에이트) 계약이 유일한 합법 경로 |
| 점포 단위 카드매출 · 유동인구 | 없음(상권 · 행정동 집계만) | 서울 상권분석(상권 × 업종 매출)을 동네 단위 신호로만 |

## 붙일 때 공통으로 주의할 것

1. 이관된 인허가 데이터의 좌표는 **EPSG:5174**(보정계수 없는 중부원점 TM)다. WGS84 로 변환한다.
2. 주소만 있는 데이터(백년가게 · 식품안심업소)는 카카오 지오코딩 결과를 저장할 수 없으므로, 인허가번호나 상호 + 도로명주소로 **이미 좌표가 있는 우리 데이터와 맞춰서** 좌표를 얻는다.
3. 관광공사 사진에는 공공누리 3유형(변경금지)이 섞여 있다. 자르거나 합성할 때 유형을 확인한다.
4. KOPIS · 서울 열린데이터(공공누리 1) · OSM(ODbL)은 출처 표시가 의무다. 약관 · 출처 목록에 추가한다(`apps/web/src/app/terms`).
5. 식품안심업소 API 는 식품안전나라 자체 키(공공데이터포털 키와 별개)이고 호출 한도가 빡빡하다. 주 1회 배치로 적재한다.

## 밤 · 새벽, 그리고 "사람들이 실제로 가는 곳" (2026-09-22)

### 밤 9시 ~ 새벽 5시에 코스가 안 나오던 문제
원인은 둘이었다: 영업시간 자료가 99% 없어서 쓰는 업종별 상식선(`data/hours/default_hours.json`)에서 식당이 21:30 에 닫고, 밤 시간대의 코스 틀이 없었다. 새벽 2시 출발은 "코스를 찾지 못했어요"(422)였다.

| 무엇을 | 어디에 | 근거 |
|---|---|---|
| 간판이 말해 주는 영업시간 `by_name` | `default_hours.json` | "24시"라고 적은 간판 786곳 → 항상, 이름이 야식 · 심야 · 포차인 집 → 17:00~03:00, 문이 없는 야외(해변 · 호수 · 둘레길 · 전망 …) → 항상 |
| 밤 시간대 `night`(21~05시)와 목적별 밤 코스 틀 | `budget.py`, `purposes.json` 의 `*-night` | 야식 → (코인노래방 · 볼링) → 밤 산책 → (야경) → (24시 카페). 식사 말고는 모두 "있으면" 자리 |
| 밤이라는 사정 `night` | `conditions.json` | 사용자가 고르지 않고 시각이 정한다. 야경 · 산책 취향을 올리고, **차로 움직이면 반경 4배**(밤 드라이브로 전망대까지) |
| 정직한 안내 `NIGHT_HOURS_ESTIMATED` | 코스 `warnings` | "간판과 이름으로 추정했으니 가기 전에 영업 여부를 확인해 주세요" |

넣지 **않은** 것: 국밥 · 해장국집(1.7만 곳)이 새벽에 여는지. 우리 DB 의 실제 영업시간 1,039건은 전부 박물관류라 근거가 없다. 추정으로 새벽 3시에 사람을 닫힌 가게로 보내는 것보다 비워 두는 편이 낫다 — 아래의 자료가 들어오면 다시 본다.

### "실제로 사람들이 많이 가는 곳" — 크롤링이 아니라 공식 실측 데이터로
네이버 · 카카오 · 구글 지도의 리뷰 수 · 방문 수를 긁어 오는 것은 약관 위반이고(이 프로젝트의 원칙), 막히면 서비스가 멈춘다. 같은 질문에 답하는 **공식 데이터**가 있다:

| 데이터 (한국관광공사, data.go.kr) | 무엇인가 | 조건 |
|---|---|---|

## 네이버 리뷰를 쓰고 싶다는 요청에 대한 판단 (2026-09-22)

**결론: 네이버 플레이스의 리뷰 · 별점 · 방문자 수는 긁어 오지 않는다.** 방법이 없어서가 아니라, 하면 서비스가 위험해진다.

| 경로 | 가능한가 | 왜 |
|---|---|---|
| 네이버 플레이스 리뷰 크롤링 | ✗ 하지 않는다 | 공식 API 가 없다. 플레이스 · 지도 페이지는 약관과 robots 로 자동 수집을 금하고, 국내 판례(잡코리아 v. 사람인, 야놀자 v. 여기어때)는 경쟁 서비스의 DB 를 크롤링해 쓰는 것을 부정경쟁 · DB 권 침해로 봤다. 막히는 날 추천 품질이 통째로 무너지는 것도 같은 문제다 |
| 누군가 모아 둔 CSV(캐글 · 깃허브 등) | ✗ | 출처가 같은 크롤링이다. 남이 긁은 것을 받아 쓰면 위험이 그대로 옮겨 온다. 시점도 낡았다 |
| **네이버 검색 API**(지역 · 블로그, 공식, 하루 25,000회) | △ 저장 없이만 | 약관이 **결과의 저장 · DB 화를 금지**한다(이 프로젝트가 처음부터 지켜 온 규칙). 그래서 "전국 80만 곳의 리뷰 수를 받아 DB 에 넣기"는 못 한다. 되는 것: 코스에 들어갈 **최종 후보 10여 곳에 대해서만, 요청 시점에** "<가게 이름> <동>" 블로그 글 수를 물어 '요즘 입소문' 신호로 쓰고 버리는 것(메모리에 그날만 캐시) |
| 네이버 데이터랩(검색어 트렌드, 공식) | △ | 가게가 아니라 검색어의 상대적 인기다. "성수동 카페"가 뜨는지는 알 수 있어도 어느 가게인지는 모른다 |
| **티맵 내비게이션 실측**(한국관광공사, 공식) | ✓ 적재 완료 | 사람들이 실제로 찾아간 곳의 순위. 위 절 참고: 7,602곳에 인기도, 3,358곳에 표식 |
| **우리 서비스의 '다녀왔어요' 별점** | ✓ 화면 완료 | 쌓이면 유일하게 온전히 우리 것인 리뷰 데이터다. 초기에 가장 공들여 모아야 하는 것 |
| 공적 표식(모범음식점 · 백년가게 · 30년 넘은 집 · 관광공사 소개) | ✓ 적재 완료 | "누군가 보증한 곳". 돈을 쓰는 장소의 54% |

**다음에 할 수 있는 것(키가 필요하다)**: 네이버 개발자센터에서 검색 API 애플리케이션을 등록해 `NAVER_SEARCH_CLIENT_ID` · `NAVER_SEARCH_CLIENT_SECRET` 을 `.env` 에 넣으면(지금은 비어 있다), 위의 "요청 시점 · 저장 없음" 입소문 신호를 붙일 수 있다. 코스 하나에 호출 10여 회 → 하루 2,000 코스까지 무료 한도 안.
