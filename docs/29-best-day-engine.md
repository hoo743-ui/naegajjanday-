# 29. "가장 가까운 코스"에서 "가장 좋은 하루"로 — 추천 엔진 v2 · 사진 파이프라인 (2026-09-22)

> 요청: 거리 제한을 hard constraint 로 쓰는 탓에 잠실 같은 넓은 지역에서도 "가까운 장소 묶음"이 나온다.
> 목적함수를 거리 최소화에서 하루 전체 경험의 최적화로 바꾸고, 사진이 잘못 붙거나 반복되는 문제를 데이터 단계에서 푼다.

### 원인
1. **거리가 세 겹의 hard 제약이다.** 고정 반경 1,200m(후보가 5개만 넘으면 넓히지 않는다) → 구간 20분 제한 → 다음 칸에 닿지 못하면 미리 제거.
   잠실 동 반경 안에 석촌호수 · 올림픽공원 · 송리단길이 없으면 그 코스는 애초에 비교되지 않는다.
2. **거리가 점수에 세 번 들어간다.** 순위의 출발점 거리, 빔의 구간 거리(도보 900m 에서 이미 0.37), λ_travel.
   "조금 더 가면 훨씬 좋은 곳"이 이길 수 없다.
3. **하루 전체를 보는 항이 약하다.** J 는 장소 점수의 평균에 업종 다양성 0.05 가 전부다.
   경험의 종류(식사 · 카페 · 활동 · 전시 · 산책 · 전망 · 밤), 전체 시간 중 이동 비율, 같은 상권 집중, 예산의 불확실성은 보지 않는다.
4. **사진은 장소 단위 엔터티가 아니다.** 검증 상태도, 같은 사진 판정(크기만 다른 사본)도 없어서, 잘못 병합된 사진과 크기만 다른 사진이 그대로 보인다.

실측 예 (수정 전, 잠실 · 데이트 · 2명 · 8만원 · 6시간 · 도보): 6시간 동안 총 이동 17분 · 1.3km. 식당 → 카페 → 오락실 → 식당.

## 1. 수정 전략
- **v1 을 덮어쓰지 않는다.** `algorithm = v1 | v2` 로 나누고, 기본값은 설정(`RECOMMENDATION_ALGORITHM`)으로 정한다. 코스 스냅샷과 추천 로그에 버전을 남긴다. 바꾸기와 순서 변경은 그 코스를 만든 버전으로 다시 계산한다.
- **거리: 제약 → 선호.**
  - hard 제약은 실행 불가능한 경우만 남긴다: 영업시간, 슬롯 시간, 예산, 좌표, 그리고 "그 수단으로는 비현실적인" 구간(도보 45분 · 대중교통 75분 · 자동차 80분, 설정값).
  - 구간 이동은 비선형 벌점이다. 수단별 "편한 구간"(도보 15분 · 대중교통 25분 · 자동차 25분)의 배수로 곡선을 정해서, 20→25분은 조금, 20→60분은 크게 잃는다.
  - 하루 가용 시간 중 이동 비율도 벌점에 넣는다.
- **적응형 탐색 반경.** 핵심 권역(동 반경)에서 인접 생활권 → 목적지 권역으로 넓힌다. 바깥 고리의 후보는 "갈 만한 가치"가 있을 때만 들어온다. 기준은 명물 · 대표 볼거리 · 공적 표식 · 실제 방문 순위 · 목적 적합도 중 하나가 뚜렷한 경우다. 그렇게 들어와도 점수로 이겨야 뽑힌다.
- **이동 성향 `move_style`**: local · balanced(기본) · explorer. 편한 구간과 탐색 고리를 조절한다. 짧은 일정은 자동으로 한 단계 좁힌다.
- **하루 점수(Best Day)** `day_score`: 목적 · 취향 · 품질 · 예산 · 시간(장소 점수 평균) + 경험 다양성 + 목적지 가치 + 자료 신뢰도 − 이동 부담 − 예산 위험(추정가 불확실성) − 일정 위험(마감 직전) − 반복 · 상권 집중. 모든 계수는 `ScoringParams.day_score`(DB 로 덮어쓸 수 있음)에 있다.
- **추천 이유 코드**를 장소마다 남긴다(PURPOSE_MATCH, BUDGET_FIT, HIGH_PLACE_QUALITY, UNIQUE_EXPERIENCE, ROUTE_BALANCE, LOCAL_SIGNIFICANCE, USER_PREFERENCE, DIVERSITY, WORTH_THE_TRIP).
- **사진은 별도 파이프라인.**
  - `place_image` 테이블에 사진마다 출처 · 출처 ID · 수집 시각 · 종류 · 검증 상태 · 같은 사진 키 · 관련도를 둔다.
  - TourAPI 원본(제목 · 주소 · 좌표)과 장소를 대조해 VERIFIED / LIKELY / UNVERIFIED / REJECTED 를 판정한다.
  - 크기만 다른 사본과 여러 장소가 나눠 쓰는 사진을 하나로 묶는다.
  - `place.thumbnail_url` · `images` 는 검증된 사진만 담는 "표시용 투영"이 된다.
  - 코스 화면은 한 코스 안에서 같은 사진이 두 번 나오지 않게 한 번 더 거른다.
  - 장소 선택은 사진을 보지 않는다.

## 4. 평가 (오프라인, `eval-courses`, 같은 파이프라인 · DB 기록 없음)
전국 quick 120 시나리오(4개 지역 × 5 목적 × 3 시작 시각 × 2 스타일):

| 사진 오매칭 · 코스 안 중복 | 0% · 0% | 0% · 0% |

이동이 늘었다고 나빠졌다고 보지 않는다(§30): 같은 이동 증가가 결함 감소 · 다양성 · 보증된 곳 증가와 함께 왔다.
CASE A(잠실 · 데이트 · 2명 · 8만원 · 6시간): 결함 없는 코스 66.7% → 100%, 경험 반복 33% → 0%, 경험 종류 3.33 → 3.67.

### 여행 지연 (고침)
원인은 같은 후보 조회의 반복이었다. 1박 홍대(데이트+친구 · 24만원 · v2) 한 요청이 `fetch` / `fetch_standouts` 를 **50번** 불렀는데 서로 다른 조회는 20개뿐이었다: 재조정 패스마다 `_collect` 를 다시 돌고, v2 구조 대안이 하루를 한 번 더 짜며 또 모으고, 둘째 날이 같은 동네를 처음부터 다시 읽었다. 조회 시간이 요청의 약 85%.
- `CandidateReads`(`place_repo`): **한 계획(`CourseService._plan`) 동안** 조회 결과를 기억한다. 키는 역할 · 중심 · 반경 · 이름 단어(표준 조회는 인기 하한 · 대표 볼거리 id까지), 날짜는 행사가 섞이는 ATTRACTION/CULTURE 에만. 중심이 옮겨지면(원하는 곳 · 걷기 좋은 구역) 키가 달라져 새로 읽는다. 제외 장소는 조회가 아니라 `hard_filter` 에서 걸러지므로 날 사이에 공유해도 된다. 돌려줄 때마다 **복사본**을 준다 — 엔진이 패스마다 buzz · local_score 를 표시하므로, 매번 새로 읽던 때와 똑같이 동작한다. 계획이 끝나면 버린다(그사이 쓰기가 없어 낡을 일이 없다).
- `fetch` 는 세 읽기(보증된 곳 · 가까운 곳 · 고르게)를 id 로만 고른 뒤, 고른 곳을 **한 번에** 관계까지 적재한다(전에는 겹치는 세 읽기가 각각 즉시 적재 쿼리 5개씩을 냈다). 순서 · 거리 필터 · 과노출 표시는 그대로.
- 결과: 1박 홍대 v2 조회 50 → 17번. 같은 프로세스에서 전/후를 번갈아 5번씩 잰 중앙값(부하가 흔들리는 개발 PC라 절대값보다 비율을 본다): **1박 홍대 v2 11.7 → 5.3초**(v1 은 5.5 → 2.7초), 1박 성수(친구 · v2) 9.6 → 6.1초, 하루 홍대 v2 13.0 → 7.3초(최솟값 7.4 → 5.8초), 하루 v1 은 반복 조회가 없어 그대로(1.7~1.9초). v2 여행이 이제 예전 v1 여행과 같은 수준이다.
- 결과 동일: 6개 요청(v1/v2 × 1박 홍대 · 하루 · 1박 성수)의 코스(장소 id · 도착 시각 · 가격 · 목적 점수)가 전후 똑같고, `eval-courses --algorithm v2 --compare quick-v2` 코스가 바뀐 시나리오 0/120, 점수표 전체가 전과 글자까지 같다. (`--algorithm v1 --compare quick-v1` 의 1건 차이 — 홍대 친구 12:00 의 당구장 — 는 이 변경 전 코드에서도 똑같이 나오는 기준선 자체의 낡음이다.)
verify 가 한 번 "이런 건 어때요?"가 사라졌다고 잡았다 — v2 가 같은 4시간에 예산을 더 쓰고 시간을 더 채워(남은 돈 12,000 → 6,000원) 더 넣을 곳이 없어진 것. 그 과정에서 시간창 초과(위 hard 제약)를 찾아 고쳤다.
