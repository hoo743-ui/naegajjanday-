# 13. 확장성 전략

## 1. 부하 특성

| 워크로드 | 성격 | 병목 | 확장 축 |
|---|---|---|---|
| 코스 생성 | CPU(빔 서치·TSP) + 공간 질의 | API CPU, DB 읽기 | API 수평 확장, 후보 캐시 |
| 메타·코스 조회·공유 | 읽기, 캐시 친화 | 거의 없음 | CDN·Redis |
| 검색·자동완성 | 읽기 | OpenSearch | 샤드·레플리카 |
| 설명·챗봇 | 외부 LLM 대기(I/O), 장시간 커넥션 | 동시 SSE 수 | API 수평 확장(비동기) |
| 수집·분석 | 배치, 외부 쿼터 제약 | API 쿼터 | 워커 수, 큐 분리 |

**트래픽 패턴**: 금·토 17~20시 피크(평시의 5~8배), 연휴 전날 급증. → 예측 가능하므로 **스케줄 기반 선제 스케일아웃** + 반응형 오토스케일 병행.

## 2. 단계별 확장 로드맵

| 단계 | 규모 | 구성 | 핵심 조치 |
|---|---|---|---|
| **1** | ~MAU 1만 · 피크 5 rps | API 2 · RDS t4g.medium Multi-AZ · Redis small | 기본 구성. 모든 폴백 경로 검증 |
| **2** | ~MAU 10만 · 피크 50 rps | API 4~12 오토스케일 · RDS r6g.large + **읽기 복제본 1** · Redis r6g.large · OpenSearch 3노드 | 읽기/쓰기 분리, 후보 캐시 적중률 ≥ 70%, CloudFront로 메타·공유 페이지 캐시 |
| **3** | ~MAU 100만 · 피크 500 rps | API 20~60 · Aurora PostgreSQL(복제본 3, 오토스케일) · Redis 클러스터 모드 · 엔진 서비스 분리 | **Recommendation Engine 분리**(→14), 로그 테이블 분리 저장, 지역별 후보 프리컴퓨트 |
| **4** | 글로벌(일본·동남아) | 멀티 리전 | 리전별 데이터 플레인, 글로벌 Identity, 다국어·다통화 |

## 3. 계층별 전략

### 3.1 애플리케이션

- **무상태**: 세션 없음(JWT), 임시 코스는 Redis. 어떤 태스크가 받아도 동일.
- 오토스케일: CPU 60% **또는** ALB 타깃당 요청 수. 스케일아웃 쿨다운 60s / 인 300s. 금·토 16:30에 최소 태스크 수를 선제 상향(스케줄 액션).
- 코스 생성 CPU 예산제: 요청당 300ms 초과 시 빔 폭 40→20→10 단계적 축소 — **과부하 시 품질을 조금 낮추고 가용성을 지킨다**(graceful degradation).
- 부하 차단: 동시 생성 요청이 임계 초과 시 `503 + Retry-After`보다 먼저, 비로그인 요청부터 큐잉(짠이: "사람이 많아요, 5초만요").

### 3.2 캐시 (가장 비용 효율 큰 레버)

| 계층 | 대상 | TTL | 무효화 |
|---|---|---|---|
| CloudFront | 정적 자산, `/meta/*`, 공유 코스 페이지(SSR) | 1h / 5m | Admin 변경 시 경로 무효화 |
| Redis L1 | 템플릿·프로필·지역 | 1h | 변경 이벤트 |
| Redis L2 | `cand:{region}:{role}:{price_bucket}` 후보 ID+피처 | 10m | 장소 승인/수정 시 지역 단위 |
| Redis L3 | 이동시간 매트릭스(geohash7 쌍) | 7d | — |
| Redis L4 | 요청 해시 → 결과 | 5m | — |
| 프로세스 메모리 | 카테고리 트리, 프롬프트 | 프로세스 수명 | 배포 |

인기 지역(홍대·성수·강남)은 요청의 60% 이상이 몰린다 → L2 적중 시 DB 질의 0회로 코스 생성. **단계 3**에서는 활성 지역×역할×가격대 후보를 배치가 미리 계산해 Redis에 적재(프리컴퓨트)한다.

캐시 스탬피드 방지: single-flight 락 + TTL jitter ±10%, stale-while-revalidate.

### 3.3 데이터베이스

1. **인덱스 우선**: `GIST(geog)`, `(region_id, status, category_id)`, 부분 인덱스 `WHERE status='approved'`. 핫 쿼리 5개는 `EXPLAIN` 스냅샷을 CI에서 비교.
2. **읽기 분리**: 추천·검색·메타는 복제본, 쓰기·직후 읽기(read-your-writes)는 primary. 세션 팩토리 2개로 Repository 레벨에서 선택.
3. **커넥션**: RDS Proxy(또는 PgBouncer transaction 모드) — Fargate 태스크가 늘어도 커넥션 폭증 방지.
4. **파티셔닝**: `recommendation_log`, `audit_log`, `chat_message` 월 파티션. 13개월 후 S3 Parquet로 아카이브 → Athena로 분석.
5. **쓰기 분산**: 로그성 쓰기는 요청 경로에서 제거 → Redis Stream/SQS 버퍼 → 배치 insert.
6. **수직 → Aurora**: 단계 3에서 Aurora PostgreSQL로 이전(복제본 오토스케일, 빠른 페일오버). PostGIS 호환.
7. **샤딩은 최후 수단**: 장소 데이터는 전국 수백만 row 수준이라 단일 클러스터로 충분. 해외 확장 시 **국가 단위 분리**(자연스러운 샤드 키)가 먼저다.

### 3.4 검색

- 인덱스 버전 + alias, 지역 수 증가에 따라 샤드 수 재조정(reindex).
- 자동완성은 별도 경량 인덱스(edge-ngram) + CDN 1분 캐시.
- 색인은 outbox 기반 비동기 → 쓰기 경로와 분리.

### 3.5 배치 · 수집

- 큐 분리(`ingest`/`stats`/`nlp`/`index`) + 큐 길이 기반 오토스케일, Fargate Spot.
- 지역 수가 늘면 수집은 **지역 단위 병렬**(잡 1개 = 지역 1개)로 선형 확장. 병목은 외부 쿼터 → provider별 토큰 버킷, 쿼터 증설 제휴.
- 증분 수집(`content_hash`)으로 지역이 10배 늘어도 일일 처리량은 변경분에 비례.

### 3.6 LLM

- 핫패스 밖 + 스트리밍이므로 API 확장성과 독립.
- provider 다중화(장애·rate limit 시 페일오버), 요청 큐 + 동시성 세마포어, prompt caching.
- 배치는 Batch API로 처리량 제한 회피.

## 4. 기능 확장성 (제품 관점)

| 확장 | 필요한 변경 |
|---|---|
| 새 목적(`회식`, `반려동물 동반`) | `purpose` + 템플릿 + 태그 선호 row → **코드 0** |
| 새 코스 역할(`SHOPPING`, `SPA`) | `category.course_role` 값 추가 + 템플릿 → 코드 0 (역할은 문자열, enum 하드코딩 없음) |
| 1박 2일 여행 | 템플릿에 `day` 필드 + 숙소 역할. 엔진은 day별 빔 서치 후 연결 |
| 날씨 반영 | `features.py`에 `weather_fit` 추가, 기상청 API provider |
| 예약·결제 연동 | 별도 Booking 컨텍스트(→14), 코스 스톱에 `booking_url`/제휴 ID |
| 그룹 투표(친구와 코스 고르기) | Course에 협업 세션, WebSocket 게이트웨이 추가 |
| B2B Open API | `api_key` + API Gateway usage plan, 동일 엔진 |
| 해외 | 통화·언어 컬럼, 국가별 provider 세트(설정), 리전 분리 |
| 네이티브 앱 | API가 BFF 없이도 모바일 친화(커서 페이지네이션, SSE) → React Native/Expo로 컴포넌트 로직 재사용 |

## 5. 용량 계획 방법

- 분기 1회 **부하 테스트**(k6): 실제 요청 분포 리플레이, 피크의 3배까지. 목표 p95 1.8s 유지 지점의 태스크 수를 기록 → 오토스케일 상한에 반영.
- 핵심 용량 지표: 태스크당 코스 생성 처리량(rps), 후보 캐시 적중률, DB 커넥션 사용률, LLM 동시성.
- 비용 가드레일: 서비스별 AWS Budgets 알람, 코스 1건당 변동비를 대시보드 KPI로 추적.
