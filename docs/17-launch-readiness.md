# 17. 출시 준비도 분석 · 검증 절차 (2026-09-21)

> 근거: 실제 API 모드에서 Chrome 으로 홈 → 위저드 → 코스 생성 → 결과 → 둘러보기 → 챗 → 로그인을 직접 눌러 본 결과와 코드 조사.
> 표기: **[확인]** 직접 확인한 사실 / **[판단]** 제품 관점의 의견.

## 0. 한 줄 진단

핵심 엔진(예산 → 코스 → 동선)과 화면 골격은 돌아간다. 그러나 지금은 **"데모가 되는 상태"이지 "서비스가 되는 상태"가 아니다.**
가장 큰 구조적 위험은 기능 부족이 아니라 **① 화면이 목(mock) 기준으로 만들어져 실제 API 와 어긋나는 문제가 반복되는 것, ② 그걸 잡아 줄 자동 검증이 0 인 것, ③ 버전 관리(git)가 없는 것**이다.
오늘 하루에만 이 유형의 버그를 6건 찾았다(목적 카드·코스 상세·둘러보기 카드·이벤트·경고 문구·태그). 사람이 눌러 보기 전에는 전부 "HTTP 200 정상"으로 보였다.

## 2. 출시 직후 품질을 좌우하는 것 (P1)

- **챗봇**: LLM 키 없으면 503 **[확인]**. 화면은 입력창을 그대로 보여 준다 → 미설정 시 메뉴에서 숨기거나 "준비 중" 처리. 키를 넣은 뒤에는 비용 상한·남용 방지(레이트리밋·프롬프트 인젝션) 점검.
- **비로그인 흐름**: 코스를 만든 뒤 저장하려면 로그인 → 돌아왔을 때 그 코스가 유지되는지 미검증. 비로그인 임시 저장(로컬)과 로그인 후 자동 귀속이 필요 **[판단]**.
- **빈 결과 처리**: 새벽에 생성하면 영업시간 필터로 슬롯이 비어 12,000원짜리 2곳 코스가 나온다 **[확인]**. "지금은 문 연 곳이 적어요 → 내일 12시로 다시 짜기" 같은 **한 번에 복구되는 제안**이 필요. 대안 탭 라벨이 "다른 분위기"로 중복되는 경우도 있다 **[확인]**.
- **모바일**: 사용자의 대부분이 모바일일 서비스인데 이번 점검은 데스크톱만 했다(창 크기 조절 실패) **[확인]**. 하단 고정 바·지도/목록 전환·안전 영역은 실기기 검증이 필요.
- **지도**: OSM 공용 타일은 운영 트래픽용이 아니다 → 카카오맵 키 또는 타일 공급자. 보행 경로도 공개 서버 → 자체 OSRM. 대중교통은 현재 "가까운 출구·정류장 + 카카오맵 링크"까지이고 환승 경로는 ODsay/TMAP 키가 필요.
- **관리자**: 통계·배너 일부 501 **[확인]**, 실 로그인으로는 한 번도 검증 못 함.
- **접근성·성능**: 포커스·aria 는 꼼꼼한 편이나 스크린리더 실사용·명도 대비 측정·Lighthouse(히어로 3,100px 핀 구간, GSAP+Motion+Lottie 동시 탑재) 미측정.
- **분석 동의**: GA4/PostHog/Mixpanel 어댑터가 있으나 쿠키·추적 동의 UI 없음.

## 3. 있으면 서비스가 달라지는 기능 ([판단], 효과 큰 순)

1. **실제 지출 피드백 루프** — 다녀온 뒤 "얼마 썼어요?" 한 번. 가격 추정의 유일한 보정 수단이자 경쟁자가 따라 하기 어려운 데이터 자산. 설계(`actual_spend` 블렌딩)는 이미 있다.
2. **카카오톡 공유 + 같이 고르기** — 약속은 혼자 정하지 않는다. 공유 링크에서 친구가 코스 후보에 투표/교체 → 확정. 바이럴 경로이기도 하다.
3. **조건 한 줄 수정 재생성** — 결과 화면에서 예산·인원·시간 칩을 바로 바꿔 다시 짜기(위저드로 돌아가지 않게).
4. **날씨·시간 인지** — 비 오면 실내 위주, 늦은 시간엔 영업 중인 곳만(지금은 조용히 빈 슬롯이 됨).
5. **예약·웨이팅·지도 앱 연계** — 장소 카드에서 네이버 예약/캐치테이블/카카오맵 딥링크.
6. **코스 중 모드** — 당일에 "다음 장소로 안내 / 여기 건너뛰기 / 남은 예산".
7. **내 주변에서 시작**(현재 위치 → `origin` 은 API 가 이미 지원) · **출발역 지정**.
8. 점주·사용자 **장소 정보 정정 제보**(가격·영업시간) — 공공데이터 공백을 메우는 두 번째 경로.

## 4. 검증 절차 — "완벽한 서비스 페이지"를 위한 게이트

원칙: **사람이 눌러 봐야만 아는 버그를 0 으로.** 아래를 순서대로 통과해야 배포한다.

### 4-1. 자동 (매 커밋, CI)
| 단계 | 도구 | 통과 기준 |
|---|---|---|
| 정적 검사 | api: `ruff` · `ruff format --check` · `mypy` / web: `eslint --max-warnings=0` · `tsc` | 경고 0 |
| API 테스트 | `pytest` (현재 198개) + 커버리지 | 전부 통과, 도메인 계층 85%+ |
| **계약 검사** | `npm run gen:api` 로 OpenAPI → 타입 생성, 생성물과 커밋본 diff | diff 0. 손으로 쓴 `types.ts` 는 단계적으로 생성 타입으로 교체 |
| **목 검증** | MSW 핸들러 응답을 OpenAPI 스키마로 검증 | 목이 실제 API 모양과 다르면 실패 → 오늘의 버그 유형을 원천 차단 |
| 빌드 | `next build`, API Docker 빌드 | 성공 |
| 보안 | 의존성 취약점 스캔, 시크릿 스캔 | high 0 |

### 4-2. E2E (매 PR, **실제 API + 시드 DB**, 목 아님)
Playwright 로 핵심 여정을 고정한다. 모든 시나리오 공통 단언: **콘솔 에러 0 · 에러 바운더리 미노출 · 가로 스크롤 0**.
1. 홈 → CTA → 위저드 4단계 → 생성 → 결과(스톱 ≥3, 합계 ≤ 예산, 지도 핀 수 = 스톱 수)
2. 결과: 스톱 교체 · 순서 변경 · 대안 탭 전환 · 공유 링크 새 탭 열기
3. 둘러보기: 전체/지역/유형 필터, 이벤트 스트립
4. 빈 결과(새벽 시각) → 안내와 복구 버튼
5. 비로그인 저장 → 로그인 → 코스 유지 (테스트용 OAuth 목 공급자)
6. 뷰포트 3종: 390×844 · 768×1024 · 1440×900 + 시각 회귀 스냅샷

### 4-3. 릴리스 전 수동 체크리스트
- 실기기: iOS Safari · Android Chrome · 카카오톡 인앱 브라우저(공유 링크의 실제 진입 경로)
- 카카오톡/슬랙에 링크 붙여 OG 미리보기 확인
- Lighthouse 모바일: 성능 ≥ 85 · 접근성 ≥ 95 · LCP < 2.5s · CLS < 0.1
- 키보드만으로 위저드 완주, 스크린리더로 결과 화면 읽기
- 외부 의존 차단 테스트: Redis · 길찾기 · LLM · 지도 타일을 각각 끊고 코스 생성이 되는지("모든 의존에 폴백" 원칙의 실증)
- 데이터 표본 검수: 지역 5곳 × 코스 3개를 사람이 읽고 "여길 실제로 가겠는가" 판정, 폐업·부적절 업종 0

### 4-4. 출시 후
에러 추적(Sentry) 알림 · 가동 모니터링 · 퍼널(위저드 시작 → 생성 → 저장/공유) 대시보드 · 주간 데이터 품질 리포트(추정가 비율, 빈 슬롯 비율, 피드백 수).

## 5. 권장 순서

1. **오늘**: `git init` + 첫 커밋 + 원격 저장소(비공개). OneDrive 밖으로 작업 폴더 이전.
2. **1주차**: 계약 검사(4-1) + Playwright 여정 1·3·4 + Sentry. → 이후의 모든 작업이 안전해진다.
3. **2주차**: 법적 페이지 · OAuth 앱 등록/검수 신청(대기 시간이 있으므로 일찍) · SEO/OG 자산 · 모바일 실기기 패스.
4. **3주차**: 실데이터 표본 검수 · 빈 결과 복구 UX · 지출 피드백 루프 · 스테이징 배포(Postgres).
5. **이후**: 3장의 기능을 1→2→3 순으로.

### 2026-09-21 — 기능 전수 점검 ("화면은 있는데 동작하지 않는 것")
방법: ① 웹의 모든 API 호출 ↔ FastAPI 라우트·스키마 대조 ② 모든 라우트의 버튼·링크·상태 코드 경로 추적 ③ `e2e/visual-audit.mjs` 캡처.

### 지도 핀이 겹칠 때 — 다른 서비스 분석과 채택안
- 구글맵·에어비앤비: 충돌 시 우선순위 낮은 마커를 숨기거나 점으로 축소 → 코스는 모든 순번이 보여야 하므로 **부적합**.
- 네이버·카카오 길찾기: 줌을 당겨 분리 → 바로 옆 가게(20m)는 최대 줌에서도 약 40px 로 핀(46px)보다 좁아 **불충분**.
- 구글어스·Leaflet Spiderfy: 겹친 마커를 방사형으로 펼치고 원위치까지 선으로 연결 → **채택**, 단 "눌러야 펼침"이 아니라 **상시 펼침**.
- 구현(`LeafletRouteMap.tsx`): 핀 상자(64×74px) 기준 2차원 충돌 판정 → 무리 중심 위쪽에 순번 순서대로 부채꼴 배치 → 제자리에 점(anchor)과 연결선(stem). 무리 속 핀은 이름표를 숨기고 선택하면 다시 보인다.

### 사진에 대한 결정
- 좌표 반경으로 아무 사진이나 가져오는 방식은 품질 통제가 안 돼 폐기(어두운 거리 사진 등).
- 현재: Wikimedia Commons "Quality images" 중심으로 후보를 모아 **사람이 한 장씩 검수한 업종 대표 사진 36장**(`apps/api/data/media/category_images.json`). 카드에 "예시 사진 · © 작가 · 라이선스" 표기. `NEXT_PUBLIC_EXAMPLE_PHOTOS=off` 로 끌 수 있다. 출시 때는 이 36장을 내려받아 자체 서빙한다(썸네일은 Wikimedia 표준 폭만 허용 — 960px 사용).
- **그 지점의 실제 사진**은 합법 경로가 제한적이다: 카카오 로드뷰 임베드(카카오 JS 키), TourAPI 실사진(관광·축제), 지도 앱 장소 페이지 링크, 점주·사용자 업로드. 네이버·카카오 플레이스 사진 크롤링/저장, 구글 Places 사진 저장은 약관상 불가.
