# 16. 전국 데이터 확보 타당성 (2026-09-21 조사)

> 표기: **[검증]** 1차 출처·실측 확인 / **[추정]** 통계 기반 추정 / **[미검증]** API 키 없이는 확인 불가.
> 원칙: 공식 Open API · 공공데이터 · 오픈 라이선스만. 지도 서비스 웹 화면 크롤링은 하지 않는다 ([07](07-data-pipeline.md)).

## 결론

공공 **벌크 데이터를 백본**으로 전국 확장이 가능하다. 장소 약 90만~110만 건, 좌표·분류·영업상태는 거의 100%.
단 **가격·영업시간·평점은 공공데이터에 거의 없다**(실측 보유율 1~5%) → "업종×지역 사전분포(추정) + 사용자 피드백 보정" 구조가 필수다.

## 필드별 커버리지 (전국 약 100만 곳 기준)

좌표 97~99% · 분류 ≈100% · 영업상태 ≈100% · **가격 실측 1~2%(추정 포함 100%)** · **영업시간 식음 3~5%** · **평점 0%(자체 피드백만)** · 이미지: 관광·축제 80%+, 식음 1~2%.

## 권장 파이프라인

1. **백본**: 상가정보(좌표·세분류·영업 중 스냅샷) + 인허가(정식 ID·폐업일·일 단위 갱신). 관광·행사는 TourAPI + 표준데이터.
2. **보강**: 착한가격(실측 메뉴가) → TourAPI(이미지·이용시간·입장료) → OSM(opening_hours, 별도 테이블) → 참가격·KOSIS(가격 prior). Google 은 사용자가 고른 장소의 **실시간 표시 전용**.
3. **중복 제거**: 같은 소스는 원본 ID, 소스 간은 geohash 블로킹 → 도로명주소 일치 가점 → 이름 정규화+거리(인허가 좌표는 건물 중심이라 주소 일치 시 100m 까지 허용).
4. **품질 필터**: 구내식당·기사식당·출장조리·편의점 등 제외 → 추천 가능 풀은 총량의 60~70%.
5. **저장소**: 약 6~10GB [추정] → 운영은 PostgreSQL + PostGIS. 로컬 SQLite 는 OneDrive 밖에 둔다.
6. **소요**: 벌크 백본 1~2일, TourAPI 상세까지 3~4주(운영키 10,000/일 전제 — **운영키 승인이 크리티컬 패스**).

## 리스크와 후속 조치

- **정책 리스크(최우선)**: [07](07-data-pipeline.md) 이 카카오를 1차 출처로 잡고 `kakao_local.py`·`naver_search.py` 가 결과를 저장하는 구조 → 2026년 약관 기준 위반 소지. 저장형 수집에서 제외하고 실시간 표시 전용으로 강등한다.
- [07] 의 품질 게이트 "가격 실측 ≥60%, 영업시간 ≥70%" 는 공공데이터만으로 **달성 불가** → "추정 포함 100%, 실측은 활성 지역 한정" 으로 재정의.
- TourAPI 법정동 코드 이관으로 areaCode 기반 조회 누락 사례 → 좌표 기반·동기화 목록 병행.
- 합법적으로 얻을 수 없는 것: 메뉴별 가격(전수), 리뷰 원문, 평점(대량), 혼잡도, 식음업 영업시간(전수).
